# Screenplay Studio — consolidated gap register and execution plan

**Purpose:** one place to see what we found across the writer journey, feedback quality, Sameer/Sushruta and supporting foundations; how we know; and what to do next. This is a planning/review artifact, not proof the entire application has been audited or fixed. Application changes have **not** started. The desired order is complete review → adversarial critique and agreement → implementation and validation.

## Evidence and test baseline

- **Full default pytest collection:** 2,248 passed, 4 skipped, 2 warnings in 97.10 seconds, using a freshly installed locked CI environment. The skipped cases are platform/applicability skips; browser E2E scripts named `e2e_browser_*.py` are not included in pytest's default collection. The suite sets the model-backed observation pass off by default except in its own tests. Many tests use mock services. Passing does not disprove the separately reproduced gaps.
- **Tracked inventory:** 665 files, including tests, documentation and assets. All 263 knowledge-base rules were mechanically inventoried; this is not a full expert review of each rule or a complete line-by-line audit of all files.
- **Real scripts:** both supplied PDFs were locally parsed and reviewed in selected passages; parser and context limitations were probed. No real model was run. A handful of paths were tested with fabricated inputs, fake clients, controlled failures or test clients; do not extrapolate frequency.
- **Unvalidated:** audience reception, real model quality/latency, cross-platform browser behavior, production incident frequency, comprehensive migration/restore safety and writer/consultant acceptance. All prior concept images are exploratory, not approved designs.

## Cross-cutting decisions

1. **Safety first, not visual polish first.** Findings 1–6 protect writer work, privacy and the truthful connection between a draft and its report. Failure of any is a stop-ship issue. Archive credentials and cross-process safety are also release-critical.
2. **A snapshot must be real, not only a label.** Capture the working draft and associated state coherently, keep inference outside the editing lock, and verify the active revision at publish. The existing per-file atomic writers do not create an atomic multi-file transaction.
3. **A reading is not a verdict.** Preserve evidence, uncertainty, counter-readings and creative intent without requiring Sushruta to agree. Sameer leads with thinking, not solutions, except on explicit request.
4. **Don't fix accuracy by deleting all hard cases.** Retain reviewable uncertainty and benchmark important missed notes alongside false alarms. Keep multilingual experts and writer intent separate from audience-response claims.
5. **Do not equate “model independent” with guaranteed quality on any model.** Evaluate multiple compatible models/hardware and report quality, variation and latency separately; do not tune to exact wording.

## One coordinated execution plan — pending the critique and approval gate

### Phase A — data safety and trust boundary
- Reproducible regression suite first for all confirmed data-loss/publication/cancellation/backup/race cases; preserve existing fixtures and demonstrate failures against current behavior.
- Design immutable working revisions, run IDs, cross-process coordination, generation publication, cancellation/retry behavior, recovery and backwards-compatible access; include backup redaction and restore policy. Define lock order and crash semantics. Preserve prior data and ambiguous legacy marks.
- Verify via actual API + CLI, two OS processes, concurrent editing, injected failure at each write, process termination/restart, disk limits, and restore. No release while a stop-ship case remains.

### Phase B — evidence, retrieval and analysis quality
- Carry exact snapshot/version and per-pass coverage into findings and chat; restore complete relevant context with bounded, measured scene windows. Resolve parser ambiguity visibly. Implement quote-match vs claim-support separation, conservative post-enrichment checks and audit trails.
- Review KB selection, assumptions, confidence language, exceptions, language filters and applied severity. Test the two scripts plus a diverse, consented held-out corpus, preserving deliberate ambiguity and independent critique.

### Phase C — collaborators and memory
- Typed neutral handoff; stable evidence/claim IDs; preferences and project scope with concurrency-safe suppression/delete; distinct personas and request-aware suggestion behavior. Check both user control and Sushruta's ability to disagree.

### Phase D — writer experience and evaluation
- Prototype one cohesive, accessible reading/discussion/revision journey, showing where each moment occurs. Test with writers and consultants before committing to the arrangement. Measure real-model quality, utility, important-issue recall, agency, privacy, completeness and latency on declared hardware and multiple configurations.
- Release incrementally behind migration/rollback controls. Assess regressions and record a clear no-go if any data-safety, privacy or misleading-evidence gate fails.

## 16–17: findings from the continued repository sweep

**16. Watch-folder processing can overwrite source files — release blocker for watch mode.** In an isolated temporary-directory test, `ProjectManifest.create` was made to fail with a simulated disk error before making a project copy. The actual `process_pending()` moved the failed screenplay to `done/`; a later failed file with the same name replaced that first source on this Linux environment. No project copies existed. The source explains why: it moves on both success and failure and `shutil.move` targets the unchanged filename. In a separate test where a project copy had already been created, that copy survived, so loss depends on the failure point. This is not a claim that the same overwrite semantics apply on every OS. **Recommended:** never treat failed work as completed; preserve the original until a verified durable project copy exists, use collision-safe no-clobber moves with explicit failure/retry and cross-process claiming, and test same-name files, partial copies, permission/disk failures and restart on supported platforms. Until fixed, avoid watch mode for irreplaceable source files and keep independently verified copies.

**17. Browser accessibility/security tests and unload saving need follow-up.** The existing live-region suite failed the repeated-identical-error DOM-write assertion twice (21 passed, 1 failed each). The app's `showError` writes the same text again, while the observer records current DOM state rather than directly proving screen-reader announcements; this failure alone does not establish whether assistive technology announces it. Verify with a reliable mutation test and real screen readers while maintaining visible, nonempty error text. The XSS suite failed a dashboard raw-HTML substring assertion twice (35 passed, 1 failed); diagnostic inspection showed `<img` in a **quoted title attribute**, not an image element, with no executable nodes, handlers or execution detected. The current failure appears to be an overly broad serialization check, **not a demonstrated XSS vulnerability**; retain the structural probe and improve test precision. The idea pagehide/autosave suite failed once when run alongside several browser suites (`len=0`), then passed in an isolated rerun (17/17). This is an intermittent test or product risk, not yet a confirmed deterministic data-loss bug. Stress-test unload, slow/network-failure and concurrent saves; avoid asserting that a keepalive request guarantees delivery. All these browser runs use the temporary Chromium setup and repository demo/fixtures, not a full accessibility, security or real-model audit.

**Additional positive coverage:** concurrent-edit browser test 8/8 and cross-project race-guard test 20/20 passed for their tested scenarios; they do not cover the distinct draft-switch, report-publication or watch-folder failures. [REPOSITORY_SWEEP_LEDGER.md](REPOSITORY_SWEEP_LEDGER.md) inventories all 665 tracked paths and conservatively marks only selected portions examined; the inventory is not a completed review.

## 18–20: writer-owned content and history (controlled storage probes)

**18. Concurrent or failed chat-session saves can lose or resurrect conversation data — release blocker for concurrent/deletion safety.** Isolated `SessionStore` tests showed: (a) after two snapshots saved, a repeated user message `Yes` was dropped because merge identifies messages by `(role, content)` rather than turn identity; (b) saving a snapshot after session deletion recreated the session; (c) a stale save after deleting a branch restored that branch; (d) when `Session.load` was made to raise a simulated transient `OSError`, saving a stale snapshot overwrote a newer stored user message; (e) when parking a damaged session as `.bak` was made to fail, save overwrote the damaged original without a backup. These are controlled store-layer reproductions, not proof that every UI flow hits them or of frequency. An in-flight chat can plausibly hold a stale session; actual HTTP timing and cross-process variants remain to be tested. **Recommended:** stable unique message/turn IDs and ordered operation-based merge; monotonic version and durable deletion tombstones for sessions/branches; prevent stale work from recreating deleted data; fail closed or preserve explicit recoverable copies if a merge read/backup fails. Clarify profile deletion independently; test simultaneous turns, repeated identical messages, cancellation, delete while in flight, backup failure, corruption and process restarts. Until fixed, avoid clearing chats or deleting branches while responses are still in flight, and preserve verified private copies of important conversations.

**19. Stash silently truncates saved writing.** Controlled call to `add_to_stash` with 4,004 characters saved exactly 4,000 and dropped the tail without an error. The UI's success path labels a successful response “Stashed,” but the precise UI selection path and user-visible frequency were not tested here. **Recommended:** preserve full text within an explicit, justified bound; reject too-large inputs before accepting them with a clear message or show a non-destructive preview and require consent to any truncation. Include Unicode, long selections, proposals and API tests. Until fixed, do not rely on Stash for passages exceeding 4,000 characters; retain the original separately.

**20. Saved beat-board order can appear current when stale.** With a saved order `[2,1]` and mocked current scene numbers `[1,2,3]`, `get_order` returned natural order while `has_board` still returned true; the stored old order remained on disk. This proves the stale-order fallback at the module level, not how a real writer would interpret a particular UI. **Recommended:** bind order to draft/scene identities; explicitly mark stale/unmatched cards and preserve the saved arrangement until the writer reconciles it. Validate same-number/different-scene changes, draft switching and reparse as well as export; never silently overwrite a stale board.

**Additional gap 13 evidence — history is not analysis truth.** Controlled `feedback_ledger.reconcile` classified a dismissed finding not re-raised as `likely_resolved`, although dismissal is not evidence of resolution. Two calls to `record_run` with empty findings but different model names produced one entry retaining the first model because the deduplication signature contains only finding IDs. These are module-level probes: the UI's wording for the former is more cautious (“you marked — and they did not come back”). Preserve each actual run by immutable run ID, deduplicate retries by operation ID only, and keep dismissed, not re-raised, changed and independently resolved distinct.

## 21, 23–27: screenplay export, multilingual evidence, PDF completeness and scene analytics

**21. Fountain/TXT export can merge adjacent speakers and change dialogue attribution — release blocker for round-trip use.** Minimal controlled Fountain example: AJAY says “Hello”; VENU says “Hi.” Parsing the original yields two speakers; the actual exporter emits no blank between the first dialogue and the next character cue, so reparsing classifies both `VENU` and `Hi.` as AJAY's dialogue. The same dialogue-block writer is used by TXT. This is not merely cosmetic: re-import/re-analysis can attribute lines to the wrong character. In local round trips of the **parsed representations** of the user's PDFs (not a fresh comparison to PDF ground truth), scene and total element counts stayed constant but Fountain changed the type of 46 elements and speaker metadata of 75 originally-dialogue elements in Darshi; Pain 3 had 30 type changes and 47 originally-dialogue speaker changes. TXT changed 48/75 and 43/47 respectively. These positional counts depend on current parser output, which itself has known uncertainties; they are not a claim that every changed attribution is independently wrong against the PDF. FDX round trips of these parsed representations retained element types/text and speaker metadata in this test. **Recommended:** delimit each dialogue block correctly; use Fountain force syntax where needed, test multi-speaker exchanges, parentheticals, multiline dialogue, forced cues and multilingual names, and verify both content and attribution after import. Also test exports in independent screenplay applications, not only our own parser. Until fixed, verify a separately retained original and any recovery export before relying on re-import.

**23. Quote verification can erase meaningful Indic vowel marks and report a different quote as an exact match.** `quotematch.normalize_text()` uses a `\w`-based filter that strips Unicode combining marks, not just punctuation. In a controlled three-word Telugu example, `కల` and `కాల` normalized to the same text; a different quote was returned as `verified` with confidence **1.0**. Similar collisions occurred in synthetic Devanagari and Tamil words. This is an actual normalization/verifier reproduction, not a measured rate for either supplied script or proof about a particular real-model output. **Recommended:** preserve grapheme clusters and meaningful script marks, use Unicode-normalized script-aware comparison, distinguish exact source-byte/codepoint matches from normalized and fuzzy matches, and evaluate false-match/false-rejection rates across languages and negation-sensitive examples. Do not label approximate matching as factual claim verification.

**24. Native Telugu speaker cues are missed in a plain-text example.** A synthetic Fountain scene with a Telugu-script character cue and Telugu dialogue parsed both as action and detected no speaker. The caseless-cue heuristic explicitly covers Devanagari and Tamil, not Telugu; Romanized Telugu and explicitly forced Fountain cues are separate paths and must not be assumed affected identically. **Recommended:** expand multilingual/caseless cue and heading support with language-aware, context-sensitive parsing and manual correction; validate on consented native-script fixtures and independently reviewed ground truth, including non-speakers and ambiguous action lines. Do not infer that all Telugu text will parse incorrectly.

**25. PDF completeness is assessed globally, so a missing page can silently escape OCR; an empty parse can still be marked complete.** A synthetic two-page PDF combined an extractable first page and an image-only second page. The actual extractor returned lines only for page 1; `parse_pdf` did not invoke OCR for page 2 or issue a page-specific omission warning, although it issued its generic low-confidence PDF warning. Separately, a scanned-only PDF with OCR explicitly unavailable returned zero scenes and an error-severity warning, while the actual orchestrator marked the parse stage `complete`. Analysis was not run in that probe. **Recommended:** inspect extraction/validity per physical page, OCR only needed pages or report them as unread, preserve page provenance and explicit coverage; block or clearly mark analysis when critical text is absent or parser errors make it unusable. Test mixed scans, extraction exceptions, partial OCR, no OCR, and correct page/scene mapping. No claim is made that the user's two supplied PDFs contain image-only pages.

**26. Character presence/interaction data can imply absence when a character is silently present.** In a synthetic screenplay AJAY stands silently beside VENU in scene 1 and speaks in scene 2. The parser's scene 1 character list contained only VENU; the knowledge graph reported AJAY only in scene 2 and no pair co-occurrence. The scene-summary prompt labels that cue-derived list `Characters`, not “speakers detected”; full scene text is also included but may be truncated in real passes. This is a deterministic candidate limitation, not proof of a model error on the user's work. **Recommended:** distinguish detected speakers, names mentioned, inferred/potential presence and unknown; preserve evidence and qualifiers, avoid asserting a silent character is absent, and let writers correct uncertain extraction. Test V.O./phone, narration and off-screen mentions as well as silent presence; do not treat simple name matching as proven physical presence.

**27. Pacing segment boundaries can misplace scenes.** A controlled document with scene ends on pages 5 and 10 produced zero scenes in segment 1–5 and both scenes in 6–10: the segment index uses `int(page // 5)` while labels are 1–5 and 6–10. The implementation also assigns a whole scene's words to its end-page segment, so per-page distribution is an estimate, not an observation. **Recommended:** define inclusive/fractional boundary semantics and test page 1, 5, 5.1, 10, long scenes crossing segments and missing pagination; label approximation explicitly rather than presenting it as precise timing.

## 28–32: collaborator interaction, context budgets and privacy

**28. Short replies can crash both collaborators before a model is called.** With a synthetic parsed script containing AJAY, the actual `extract_character_refs` raises `ValueError: max() arg is an empty sequence` for `Hi`, `Yes` and a Telugu-script input because its fuzzy candidate list has no Latin word of four or more characters. An actual `CoWriterEngine.send_message(..., 'Yes')` raised before the fake model was called and before any messages were stored. The HTTP route catches generation exceptions and presents them as model-server errors; the route itself was source-traced, not exercised in this probe. Named characters and other inputs can avoid this particular error; impact depends on input and script. **Recommended:** handle empty candidate lists, use Unicode-aware matching without inventing names, gracefully fall back to no character match, and test short affirmations, native-script utterances, punctuation and explicitly referenced scenes through both streaming and non-streaming APIs.

**29. Reply filtering can erase a direct answer.** With a fake model returning “Subtitles can help the audience follow the scene” in response to “Should I use subtitles?”, the actual engine returned and appended an empty assistant message to the in-memory session: `clean_reply` removes any sentence containing `subtitle`. This demonstrates a deterministic transformation of a fabricated answer, not real-model performance or user preference on subtitles. **Recommended:** distinguish irrelevant unsolicited language commentary from a writer's explicit request; preserve requested answers and legitimate craft observations. Never silently deliver a blank result after cleaning; show a recoverable failure or retry deliberately. Keep stored history truthful and label any presentation transforms.

**30. The turn's actual model payload can exceed its declared prompt budget.** In a synthetic 30,000-character scene with `prompt_budget=2048`, the actual engine emitted a warning that its base prompt was already above the requested budget, then appended scene context; the system message was about 39,117 characters and all messages about 39,508 characters. This proves that budget is not a hard bound on the complete payload; it does not prove how any particular model server handles it. **Recommended:** calculate an end-to-end model/token-aware budget including system instructions, scenes, quoted passage, history and reserved output; preserve explicitly requested context by measured windowing, disclose omissions to the writer, and fail clearly if a required minimum cannot fit. Compare models/tokenizers; do not claim character counts guarantee tokens or that shortening improves quality.

**31. Other projects' details can enter a current-project model prompt.** The actual webapp supplies a library provider for project chats. In a temporary synthetic shelf, passing the actual library digest into the actual engine placed another project's title and character name in the captured fake-client prompt. The provider can also include theme-finding text; the doctor may receive cross-project aggregate patterns. The digest can be shed under prompt pressure. This establishes prompt inclusion, not an actual external transmission, an unauthorized access incident, or what a model later said. **Recommended:** make cross-project context opt-in or per-project configurable, preview its scope before any remote transmission, keep project boundaries explicit, and provide a genuinely local-only mode. A prompt instruction not to confuse projects is not a privacy boundary. Do not send private screenplays or their digests to an outside provider without explicit consent.

**32. Streaming can display raw model content before guards, including `reasoning_content`.** A fake SSE response containing a `reasoning_content` fragment followed by `content` was passed through the actual chat client as both streamed pieces and the concatenated reply. The current browser app displays token events immediately; cleaning and verification happen after generation. The non-streaming client also falls back to `reasoning_content` when ordinary content is empty. This is a synthetic transport test, not proof a real provider returned such fields. **Recommended:** do not treat hidden reasoning fields as an answer; handle models that produce no final content explicitly. Decide whether to buffer sensitive/attribution-sensitive segments or clearly mark a provisional stream until validation, keeping latency and user comprehension measurable. Ensure final stored output, history and visible output remain consistent and no unverified quote appears as verified merely because it streamed first.

## 33–36: connection security and recovery sweep

**33. Validated model URLs can redirect private payloads beyond the allowed boundary.** A controlled test of the actual analyzer `BaseLlamaClient._post_chat` used two local servers: the first returned HTTP 307 to `outside.example`, a hostname the URL guard rejected when tested directly. Monkeypatched DNS mapped that name to the second loopback server, which received the synthetic chat payload. No external host was contacted and no real data was used. This demonstrates an unvalidated redirect hop, not actual exfiltration; it requires an endpoint that issues or is made to issue the redirect. Additional controlled 307 tests of the actual collaborator synchronous client, collaborator streaming client and external STT client also delivered synthetic chat, streaming-chat and audio payloads to the DNS-remapped loopback destination. No actual remote destination was contacted. Requests also ordinarily consults proxy environment settings; proxy effects and credential-header behavior remain to be tested, not assumed. **Recommendation:** define permitted destination and consent policy for every transport, explicitly disable redirects or validate and pin each hop before sending any body, reject unsafe scheme changes, and account for DNS resolution/rebinding, proxies, provider compatibility, streaming and STT. Test local and explicitly consented remote providers, 30x variants and proxy setups without transmitting private scripts. Do not imply initial URL validation alone guarantees the payload stays local.

**34. Credential and archive boundaries remain unsafe or underspecified.** In an isolated test with process umask `022`, saving a manifest containing a synthetic API key produced `project.json` with mode `0644`. Actual accessibility also depends on every parent directory's permissions, platform and ACLs; this does not demonstrate access to anyone's real key. As already reproduced above, project and library archives include stored synthetic keys. In a separate temporary-project test, both real backup endpoints followed a file symlink inside a project and included the synthetic contents of its target outside the project tree. This requires such a link to be present; no remote attacker or actual secret access has been demonstrated. **Recommendation:** prefer OS credential storage or another supported secret mechanism; avoid returning or archiving secrets by default, define secure migration, deletion, backup/restore behavior and platform-specific permissions. For archives use an explicit member policy, reject or safely record symlinks without dereferencing targets, verify containment and completeness, and clearly explain exclusions. Do not silently strip writer-owned material or promise an encrypted backup without actually implementing and testing one.

**35. Opening the sample can overwrite a damaged project.** In a disposable project directory named `The_Late_Hour`, a malformed synthetic `project.json`, synthetic source and synthetic parsed file were created. This is a recovery hazard for that name and damaged/unreadable state, not evidence that all projects are overwritten. **Recommendation:** never recreate over an existing unreadable directory; surface recoverable damage, preserve it intact, and create the sample in a separately claimed collision-safe directory. Test corrupt manifests, transient access errors, concurrent creation, reserved-name collisions and restart.

**36. Model context limits can remain stale when a server changes.** A synthetic test against the actual `BaseLlamaClient` populated the global context-window cache for a URL with 8,192, then created another client at the same URL whose mocked probe would return 2,048. The second client still returned 8,192 without probing. This proves the URL-keyed cache does not notice that simulated change, not that any particular user's server has changed. Depending on the replacement model/server, stale capability information may cause oversized or unnecessarily constrained requests. **Recommendation:** tie cached capabilities to an identified server/model generation, invalidate on configuration/reconnect/failure or use bounded freshness, and handle provider rejection gracefully. Test model swaps and restarts at the same endpoint and consider probe latency/offline behavior.

## 43–47: deterministic craft claims and report completeness

**43. Directness can be purposeful; the writer and readers may disagree about its effect. **Recommendation:** treat literal expression as an optional observation or context-sensitive question, not proof of absent subtext or poor writing; compare against deliberate confession, comic, truthful and withholding scenes with independent readers. Do not categorically ban useful directness or criticism.

**44. Ordinary day/night scene headings can be reported as a missing transition.** In a two-scene synthetic script, `INT. KITCHEN - DAY` followed by `EXT. STREET - NIGHT` produced an “Unmarked time flip” finding even though each heading explicitly specifies its time. **45. **46. But same rule/scene or related rules do not establish that the same claim or passage is involved, and a primary count or reading can conflate them. **Recommendation:** group only with meaningful claim/evidence correspondence; preserve independently reviewable judgments and indicate uncertainty. Test separate lines, opposite claims, related rules and transitive clusters, including writer verdicts and counts.

**47. Exported Markdown can say “No significant findings” for a failed or unrun category.** Rendering a synthetic `AnalysisResult` with dialogue marked failed and an error produced a dialogue section saying exactly that phrase; the global error was also present. Source renders the same empty-category text without checking category outcome. This is a report-renderer reproduction, not a claim about every UI surface. **Recommendation:** distinguish not requested, prerequisite unavailable, failed, partial and successfully evaluated with no findings, at category and coverage scope. ## 60: model-call deadlines under contention

**60. This is distinct from guaranteeing a hard stop of an already-running synchronous request: normal Requests timeouts are not necessarily a total end-to-end deadline. **Recommendation:** carry one monotonic deadline and cancellation signal through discovery, retry, backoff and each transport attempt, stop scheduling work after expiry, and distinguish a deadline for returning control from provider-side cancellation. Bound streaming/read behavior and expose actual terminal status without discarding a previous valid report. Evaluate queue fairness and realistic high-load latency rather than simply eliminating retries. Existing `test_generation_timeout.py` and client tests passed **14 tests** but did not cover this nested-busy scenario.

## 61–69: draft lifecycle, workspace confinement and store-lock sweep

**61. Concurrent draft uploads share one temp file and one swap target.** Two synchronized synthetic concurrent requests to the real Flask route `/api/projects/Test/drafts`, each staged at `_draft_upload.<ext>` and swapping `source.fountain.incoming`, returned A = 200 with the manifest naming A while the active source held B's text and none of A's, and B = 500 because A's cleanup had already removed the shared temp file. A second controlled interleaving made one upload succeed and the other 500 while only one draft record was written. Ordering was forced by a barrier, so frequency is unknown; no private data was used. **Recommendation:** give each upload an unguessable per-request staging file, serialize draft mutation per project, and make snapshot + swap + manifest write one recoverable transaction. Note that unique temp names alone do not fix the swap and manifest races.

**62. Draft names are not validated against the drafts directory, so activation can read and overwrite another project's files.** *FIXED 2026-11-04 — `draft_dir()` now validates the name at the single chokepoint; see §21 of `SELF_CRITIQUE_OF_GAP_REGISTER.md` for the fix, the attack test and the correction that `/diff` and `/compare` were a second, worse vector than this entry described.* `draft_dir()` joins the request-supplied name onto `drafts/` with no containment check (`activate_draft_endpoint` strips whitespace only). In a synthetic two-project workspace, `POST /api/projects/Alpha/drafts/activate` with a relative name reaching a sibling project's `drafts` folder returned 200, replaced Alpha's source and report with the sibling's snapshot, recorded that name as `active_draft`, revealed the sibling's report text through `/api/Alpha/report`, and exposed both snapshot trees through `/diff` and `/compare` with traversal names. A name resolving outside `PROJECTS_DIR` was read the same way, and opening a write session on that state copied Alpha's later uploaded draft text into the outside directory's `source.fountain`. Names that resolve to a directory without `parsed.json`, or to the project's own path, fail safely (400 or `SameFileError`), so this needs a crafted API name rather than the draft picker. The underlying hole is both path traversal and a missing per-project confinement rule, and `diff.py` has no name validation of its own. **Recommendation:** validate with `check_safe_id`, resolve real paths and require containment inside the project's own `drafts/`, reject separators and reserved names, apply the same rule to activation, diff, compare and every draft reader, and add traversal tests. Treat this as a workspace-integrity defect, not a display bug.

**63. Draft switch restores only some derived files, so the knowledge graph and other artifacts stay bound to the outgoing draft.** *FIXED 2026-11-04 — the whole per-snapshot bundle moves with the draft; see critique §28.* Activating a previously snapshotted draft restored `parsed.json`, the report pair and the source, but the snapshot directory holds no knowledge graph and the graph file was never restored. In a controlled two-draft project the `/characters` endpoint returned BETA STRANGER after switching back to ALPHA, whose source and parse were correct; the parsed document lacks a `heading` key, so this may also silently degrade heading-dependent UI. **Recommendation:** treat a draft as one immutable bundle with a manifest of every derived artifact, restore the whole bundle atomically or leave it absent and visibly stale, and invalidate dependants on switch; test characters, scene analytics, beat board, findings and chat context after switching.

**64. A failed draft upload is accepted into the project and can strand the writer on a broken active draft.** Uploading a non-screenplay `.fdx` returned 500 but had already made the bad file the active draft with parse `failed`, discarded working edits, and reset analysis; the previous good report remained on disk while `/report` answered 400. After a re-activation of the good draft the source and parsed data were correct, but the parse stage stayed `failed`, so `/script` still refused with “Project hasn't been parsed yet”. Only a manual reparse restored it. A `/script` document additionally returns scene `heading: None` because the field is `heading_raw`, so heading-driven recovery UI should not rely on the serialized key. **Recommendation:** validate a draft in a quarantined area before making it active, keep the previous active draft reachable in one step on failure, restore stage status from the restored snapshot rather than the last attempt, and test every supported format's rejection path.

**65. An analysis already running can publish findings for the draft it started on after the writer has switched drafts.** *NARROWED 2026-11-04 — switching is refused with 409 while a run holds the analysis lock; a cross-process publish is still possible, so this is not closed; see critique §28.* With a stubbed long-running analyzer and a real draft upload during the run, the upload returned 200 and re-queued analysis, but the finishing run then wrote its report and marked analysis `complete` for the ACTIVE draft; `/report` served the old draft's finding while `/script` served the new draft's text. The reverse hazard is the cancelled-run restore path and the already-recorded overwrite of a prior report on failure. **Recommendation:** bind each run to an immutable snapshot ID and refuse to publish if the active snapshot changed, or publish the report *into that snapshot* and tell the writer which draft it describes; make draft mutation take the same per-project analysis lock the run holds.

**66. Draft upload and activation bypass the per-project analysis lock.** The `_analyze_lock` is taken only by `/analyze` and `/analyze/retry-failed` (gap 65's hazard), and `/analyze/cancel` decides “is anything running?” by looking for a cancel event that only `/analyze` creates. During a real `retry-failed` run, `/analyze/cancel` answered 409 “No analysis is running for this project”, so a resumed retry cannot be stopped. **Recommendation:** use one per-project operation lock for analysis, retry, draft mutation and restore, expose a single truthful running state (with what it is running on), and make cancellation work for every long-running operation.

**68. Lock budgets are not honored for in-process contention.** A held `lock_for` path, a 0.05 s `lock_deadline`, and a same-process waiter: the waiter acquired the lock after the full 3-second hold rather than timing out at 0.05 s, because the outer `RLock` is acquired with no timeout. Cross-process contention with the same budget timed out correctly at 0.1 s, and uncontended acquisition is immediate. So a stuck or very slow writer in the same process is bounded only by the OS lock path, and the designed “one budget for the cycle” guarantee is not uniform. This is a latency/correctness-of-message issue, not a data-loss one. **Recommendation:** give the in-process gate a deadline-aware acquire, keep reentrancy, report which wait actually expired, and test nested cycles, same-thread reentry, busy waits and cancellation against the configured budget.

**69. Busy-store handling of a completed analysis replaces a successful result with a transient warning.** With a completed report on disk and the metrics write mocked to raise `StoreLockTimeout`, `POST /analyze` answered 503 `busy` after the analysis had already succeeded, which invites the client to re-run a finished job. The report survived. This is a controlled mock, not proof of a writer hitting it. **Recommendation:** record telemetry and history best-effort outside the success answer, label the returned state distinctly (completed with a skipped side record), and make “busy” mean the operation did not start.

Test baseline for this batch: 60 tests in `test_diff`, `test_destructive_paths`, `test_store_busy`, `test_store_concurrency`, `test_lock_order` passed; existing suites do not cover gaps 61–69.

## 70–74: persistence, backup and idea-store sweep

**70. A damaged `idea.json` is shown but cannot be repaired through the app, and saves fail as a request error.** After corrupting a synthetic idea file, `GET /api/ideas` still listed it (flagged, by design), `GET /api/ideas/<id>` and `POST .../content` both answered 400 with the raw `JSONDecodeError` text, and the file was left untouched. The project side handles the same damage as 503 `unreadable` with a clear message; the idea store raises the parser error instead, so the writer sees “Expecting property name…” as if their request were malformed, and there is no in-app way to recover the page. **Recommendation:** route idea reads through the shared store reader, answer a distinguishable damage state, preserve the file, and offer export/repair of the raw text rather than a dead end.

**71. Library backup includes the idea store labelled as a project, and omits the writer's relationship memory.** In a synthetic library the archive's own manifest listed `ideas` as a project entry, and `writer_profile.json` was not included (the shelf-listing exclusion is reused for backup). Project archives also silently skip unreadable files and any file that vanishes mid-zip. This repeats and extends gap 8's scope question: I found no restore/import route for either archive. **Recommendation:** decide explicitly what a library backup means, label ideas/memory as their own sections, account for every skipped file in the manifest, and treat restore as part of the backup feature. (Whether relationship memory *should* be in a backup is a privacy decision for the writer, not a default to leave implied.)

**72. A successful archive can be incomplete without telling the writer.** Both backup routes wrap `zf.write` in `except OSError: continue`, and the per-project archive does not even keep a count. The gap-8 probe already showed a skipped file with a 200; the library archive counts files but not omissions. **73. Export does not disclose a stale or foreign source file beside the active one.** A project with a leftover `source.pdf` next to the active `source.fountain` exported the active working copy correctly with no warning, and nothing in the UI explains that the extra file exists and is not part of the active draft. This is a minor provenance/clarity issue, not corruption. **Recommendation:** make the active source file explicit in the project's own metadata and surface stray source-format files as unattached material rather than leaving them to be discovered in the folder.

**74. `ProjectManifest.save` stages treat any change inside one stage as a whole-stage overwrite, so a long-held object can revert a newer stage error or error field.** Two successive saves from separately loaded objects kept both writers' values only where the whole stage dict differed from the baseline; a controlled probe showed a stale object's `parse` status winning and then separately reverting an `error` field written by another object. Per-stage merging is documented and does prevent cross-stage clobber, but it still has last-full-stage-writer-wins semantics within a stage. **Recommendation:** give stages their own revision or field-level merge, and make “a run finished” a compare-and-set on the snapshot it ran for. Existing tests do not cover two objects writing different fields of the same stage. Follow-on clause (was a separate entry, merged because it is the same mechanism at a finer grain): concurrent saves of the same nested stage data are last-writer-wins at the field level — `output_paths` is replaced wholesale, so a peer's partial record disappears with no conflict signal; merge per key instead of per stage.
## 77–79: deterministic continuity and export containment sweep

**77. Continuity flags a day/night cut under an action heading as a "dropped transition".** A two-scene synthetic script (`INT. KITCHEN - DAY` then `INT. GARAGE - NIGHT`) produced an "Unmarked time flip" finding whose own evidence quote is the second scene's heading — a heading that *states* the new time. Severity is low, so it reads as advice rather than an error, but it is a claim the parser cannot support and it lands in the same continuity category as real mechanical errors. On the parsed Pain 3, three of these fire (scenes 5→6, 13→14, 17→18) and each is a normal act/scene cut. This corroborates and sharpens gap 44's pacing/time finding from the opposite side: the writer is told a cut they wrote deliberately is missing. **Recommendation:** distinguish cuts, act breaks and passages of time from genuinely ambiguous day/night swaps, state the uncertainty, and never quote the new heading as evidence that the transition is absent.

**78. The character-name variant check is a 2-edit-distance guess that produces confident nonsense.** `_looks_like_variant` compares any two speaking names with Levenshtein ≤ 2 or a short prefix, then only requires that they never share a scene. A synthetic `MOTHER` / `BROTHER` pair (different people, never together) produced "look like two spellings of the same character"; the check has no alias, family, or title awareness. It is low severity and phrased as a question, but the writer sees a "corrupts the knowledge graph" explanation for a false positive. Pain 3's parsed cast is `SIDDHARTH` with no `SIDDHU` cue, so the attached script does not exercise this branch; the real names appear only inside headings and action, and export retains them (13 `SIDDHU` occurrences in FDX and Fountain). **Recommendation:** require corroboration (same surname, near-identical dialogue context, a shared scene-adjacent history), downgrade unchecked pairs to a silent parse note, and let the writer confirm/merge aliases explicitly. Do not present a heuristic guess as a continuity defect.

**79. Export and revision never print a source-provenance line, and re-import cannot tell reconstructed from original.** A parsed PDF exports cleanly to Fountain and FDX, but nothing in either artifact records that it was reconstructed from a PDF parse, which parse generation produced it, or what was lost (FDX loses bold and non-numeric scene numbering — a documented format limit, not a gap; PDFs may omit image-only pages per gap 25). A writer handing a re-export to a collaborator cannot tell it from an original. **Recommendation:** embed a machine-readable and human-readable provenance block where the format allows (FDX title-page metadata, Fountain boneyard comment), keep it out of the rendered page where it does not, and include export provenance in the backup manifest. Test that a re-import ignores the block cleanly.

Test baseline: continuity checks exercised directly on synthetic text and on the parsed attached scripts; export containment checked on the parsed Pain 3. No existing test covers gaps 77–79.

## 80–82: shelf damage handling and act bucketing

**80. A damaged project shows as "unreadable" on the shelf and then refuses to open — with no recovery path.** A synthetic project whose `project.json` was corrupted appears in `GET /api/projects` flagged `unreadable: true` (good), but the SPA then answers every open with "This project's files are damaged on disk and can't be opened", and there is no export, repair, or raw-copy action for that project. Its source and parse may still be perfectly intact, and backup also refuses (`/backup`, `/script` and `/drafts` all answer 503 "project.json is damaged and was not touched"), because every route loads the manifest first — including the one that would copy the folder out. **Recommendation:** treat an unreadable manifest as a *recovery* state, not a dead card: offer to back up the folder as-is, read the source file directly, and rebuild a manifest from what is on disk while preserving the damaged file. Keep the warning; remove the dead end. This is the same dead-end shape as gap 70 on the idea side.

**81. Act bucketing collapses to two non-empty acts for short scripts and labels the empty act anyway.** A three-scene synthetic excerpt produced acts with 0 / 2 / 1 scenes, and the first act's `page_start` is `1.0` while every scene's estimated page is `0.1`, so the numbering is internally inconsistent. On both attached parsed scripts the bucketing is sensible (Darshi 1/7/3, Pain 3 7/11/4), so this is a small-script and proxy-pagination defect rather than a general mis-bucketing: the percentages assume feature length. **Recommendation:** state that acts are proportional estimates, hide empty acts, use the same page unit for scene positions and act bounds, and do not present act structure as if it were authored. Any act-based navigation in the proposed journey must therefore label it an estimate.

**82. The shelf and the idea shelf use different damage vocabularies for the same idea.** `GET /api/projects` flags a damaged project with an `unreadable` key and empty stage objects; `GET /api/ideas` flags a damaged idea with `unreadable` and a title equal to its id. The UI handles both, but the payloads differ enough that any future shared recovery surface would need two shapes. **Recommendation:** define one damage envelope (`{id, title, unreadable, recoverable, detail, last_known}`) used by every shelf, so recovery UI and support tooling can treat them uniformly. Low severity; it is a prerequisite for gap 80's fix rather than a separate product risk.

## 83–86: documentation and CLI surface drift

**83. The CLI documented surface and the shipped CLI disagree on top-level commands.** `python -m screenplay_studio --help` offers exactly `run, resume, status, watch`. The route map's own conventions and several docs describe a wider toolchain; more importantly, `docs/API_ROUTE_MAP.md` states there is "no standalone `server.py`" while `screenplay_cowriter/server.py` still exists, still parses arguments, and still binds loopback on 8300 (verified by `--help` and by source). `docs/CLI_REFERENCE.md`, `docs/ARCHITECTURE.md`, `docs/CODEBASE_MAP.md` and `docs/PROJECT_MEMORY.md` all still present the co-writer server as a supported surface, and `AGENTS.md` says the only HTTP servers are the webapp and the demo model. If it stays, give it the same capability-token/Host guard the webapp uses and document it as a second front door onto the same data. **85. `docs/API_ROUTE_MAP.md` conventions are themselves inaccurate about the port and the process model.** The header says the map is authoritative for a process "on port 8500" while the same file's totals and the SPA describe a single Flask process serving both API and static SPA; the demo model is described as a separate app, which matches source. Cosmetic, but it is the kind of file that later gets loaded "because it's there".

## 87–90: end-to-end demo run, report honesty and refresh behaviour

For the first time in this sweep the **whole pipeline was run end to end against the built-in demo craft model** on a two-scene synthetic script (loopback only, no real model, no private data). Everything below comes from that run plus source traces. It is still not a quality or accuracy measurement.

**87. A report can present an invented narrative detail as a finding against the writer's script, and the writer-facing report never says it is unsupported.** The demo model returned a setup/payoff line about "the revolver", which appears nowhere in the two-scene script. It survives into the stored report, the served `/report` and `/fixqueue` payloads, and the rendered Markdown as a plain "[LOW] Scene 1, Scene 2 — Setup left dangling: 'The revolver'". It *is* flagged `ungrounded: true` in JSON and default-hidden in the fix-queue UI, which is real mitigation — but the Markdown report a writer exports or reads never mentions `ungrounded`, verification status or observation coverage, so the same sentence reads as a finding in one surface and as a hidden guess in another. The quote-bearing rate in this run was 1 of 6 and the observation rate 0 of 6. **Recommendation:** carry the evidentiary tier (quote / observation / none) into every rendered surface including Markdown and export, not only the JSON and the dock; keep the default-hide behaviour but state the hidden count where the visible list is shown; and treat "names something absent from the script" as its own verifiable defect class rather than letting it pass as a low-severity opinion.

**88. Demo-mode output is disclosed by name, not by nature, in the exported report.** The Markdown said "Analyzed with: `demo-craft-model`" and individual rows carried a `[demo]` prefix, while the first line of the body said "a demo model is running, not a real analysis" only in one section. Given gap 59 (historical disclosure follows current global state), the honest minimum is that every stored/exported report states the provider and whether it was the built-in stand-in, from the run's own record. `model_used` is persisted, so the data exists; the renderer just does not use it for the disclosure banner. **Recommendation:** render the stand-in disclosure from `model_used` at generation time and store it in the Markdown itself, so an archive stays truthful after the setting changes.

**89. Deterministic findings and model findings are indistinguishable in the writer-facing report.** In the same run the continuity "unmarked time flip" row (deterministic, and per gap 77 a weak inference) sat beside demo-model rows in one list with identical severity styling and no marker of origin or confidence. The JSON distinguishes them only by accident of content. **Recommendation:** label provenance in the rendered report — deterministic rule, model judgment, or model-with-evidence — and let the writer filter on it. This is the report-side half of the "separate claim, evidence, provenance" requirement in the critique.

**90. Refreshing the desk after a complete analysis is a second full pass, and the run leaves the process holding a demo server that outlives the mode switch.** During the demo run, `start_demo_server()` bound 8099 in-process and stayed up for the life of the process (documented and deliberate, but it means a stopped demo *mode* is not a stopped demo *server*). The UI's post-analysis refresh re-reads script, edits, drafts, notes and report through five parallel requests; each re-loads and re-merges the manifest and re-stamps scene keys. On this tiny script that is trivial; the cost that matters is that a report is only re-rendered at generation time, so the report file and the desk's live view can describe different states (already recorded as gap 1's family). **Recommendation:** treat the report as an immutable generation artifact with a pointer, and when the UI needs the freshness badge, derive it rather than rewriting the artifact; document the demo server's lifetime in the connection panel so a writer knows why a port is still open after choosing a real model.

Related: `_observation_coverage` reports "0 of 6" while the visible list shows 6 rows; that arithmetic is only honest if the report says which rows are hidden. Existing demo-model tests pass and do not assert any of the above.

## 98–101: collaborator turn classification, safety prompts and memory scope

**98. Turn classification treats an intent statement as a bare idea, so the collaborator interrogates a writer who just told it what they meant.** `classify_turn` keys on the first word and a trailing question mark only. Measured on the real functions: "Let the silence sit." → `idea`; "I want the audience to feel compulsion." → `idea`; both are then **probed** ("why do you think so?"). By contrast "Can we talk about the mother?" and "Could I lose the last beat?" are classified `question` because they start with a modal, so an exploratory request becomes a question turn and a stated intention becomes a probe target. This is precisely the failure the user's brief rules out: Sameer should not interrogate when the writer has already said what they want or asked something. The reasoning carve-out works only when a connective like "because" is present ("I cut the line." alone still classifies `idea`). **Recommendation:** classify on intent cues, not the first token — add imperative/statement patterns for "let", "I want", "I'd like", "keep", "allow", and treat modal+verb as a request for help rather than a fact question. Keep the probe for genuine undeveloped ideas only, and cover this table with a regression test that uses the writer's own Darshi/Pain 3 phrasing.

**99. The safety contract for the probe path lives in prompt text only.** `PROBE_SYSTEM_PROMPT` instructs the model to reflect, ask one question and avoid suggestions; that is a good instruction, but nothing deterministic enforces it on the reply. `ensure_forward_momentum` and `cap_suggestions` do post-process, yet they operate on heuristics applied after generation, and the same is true of `reply_transforms`. A model that answers with three suggestions on a probe turn will be partly trimmed, not prevented, and the writer's first impression of Sameer is set by that turn. **Recommendation:** treat the first turn as a contract with a post-check (reflection present, exactly one question, no offer), and when it fails, regenerate once with the violation named rather than silently trimming. Keep the prompt as the primary mechanism.

**100. Craft history can only cite edits that are still applied, so a writer who tries something and reverts it looks like they never did it.** `craft_history` reads `edits.json`, which holds only in-effect edits because undo pops the record onto the redo stack. That is documented honestly in the module, and it is the safest available reading — but it means the collaborator's "last time you cut the explainer line" evidence is silently one-sided: deliberate experiments the writer reversed are invisible, and a writer who undoes a lot will have almost no craft history despite a month of work. **Recommendation:** keep the in-effect rule for what may be *cited*, but derive a separate, never-quoted "experiment count" from the undo/redo stacks so the memory refresh can distinguish "this writer rarely changes lines" from "this writer tries and reverts constantly". Do not let either number become a claim about the person.

**101. Several persona-visible behaviours are decided by substring rules that the writer will read as the collaborator's character.** `has_embedded_reasoning` matches words like "since" and "so that", which also occur in ordinary narration ("since the funeral, he…"); `classify_turn`'s directive list misses polite forms ("could you tighten this", "would you try…") that then route down the question path. These are cheap to fix and high-leverage, because every misfire is experienced as the collaborator not listening. **Recommendation:** replace the substring tests with a small, tested intent table covering requests, permissions, statements of intent, reasoned choices and pure ideas in English, Tenglish and Hinglish (the product already claims those registers), and log the classification per turn locally so a writer's report of "it didn't answer me" can be traced. This pairs with gap 98 and should be implemented as one unit.

Test baseline: pure-function probes of `classify_turn`, `should_probe` and `has_embedded_reasoning`, plus source traces of the probe path and craft-history scope. No model was called; the demo transcripts in gap 92 show what a stand-in does, not what the classification rules guarantee.

## Product direction — the intent problem, stated once without a gap number

The analysis is **intent-blind**: `save_project_premise` persists `premise.json`, the graduation route carries it,
and the collaborator's prompt builder accepts `premise=`, but `Orchestrator.run_analyze` → `pipeline.analyze` takes
only document, client and language options, and "premise"/"intent" appear in `pipeline.py` and `prompts.py` only as
*output* concepts. Scene-level intent has nowhere to live; dismissal records a judgment that feeds back only as a
hidden row. So a writer can state what they meant — in prose meant for this purpose — and neither collaborator
hears it.

That is a product decision for the writer and the collaborator designs to make, not a defect, and it cannot be
validated here without a real model. If it is taken up, the shape is: a scoped, structured intent brief (premise
card + per-scene intent + deliberate flags) passed into the relevant passes; the model stating the intent it
believes it is judging; findings that conflict with stated intent surfaced as *disagreements to discuss* rather
than defects; and Sameer exploring intent while Sushruta tests it against evidence. Evaluated on the writer's own
material, not by this sweep.

**Also product direction:** a writer-facing recovery surface (97's substance). Each failure is honest in its own
endpoint — 503 "not touched", 400 with a reason — but none offers the next action. That is a journey decision, and
the underlying defects are already numbered (80, 82, 70, 64, 72).
